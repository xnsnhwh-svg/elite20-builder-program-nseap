# 每次迭代后的产品自查清单

这份清单用于每次完成一版 MVP 或功能更新后自查，避免只关注“做了什么功能”，而忘记回到产品目标和用户价值。

## 一、先问目标用户

1. 这一版主要服务谁？
   - 学生 / Builder
   - 老师 / 课程组织者
   - Knowledge Team
   - Agent / 平台系统

2. 这个用户现在最痛的点是什么？
   - 资料太散，找不到。
   - 上传后没人整理。
   - 不知道资料属于课程、挑战、案例还是提示词。
   - Agent 后续无法可靠调用。

3. 这一版有没有真的帮助这个用户？
   - 是让他更快上传？
   - 更快找到？
   - 更快整理？
   - 更快复用？
   - 还是只是多了一个页面或按钮？

## 二、再问用户价值

1. 这次迭代给用户带来的直接价值是什么？

2. 用户使用后，能不能明显少做一步？

3. 用户是否更容易把零散资料变成结构化知识？

4. 老师是否更容易看懂这个模块的作用？

5. 这个能力是否能为后续 Agent 检索提供更好的数据基础？

## 三、检查产品目标

本模块的目标不是做普通文件夹，而是把资料沉淀成可检索、可分类、可复用、可被 Agent 调用的知识资产。

每次迭代后都要问：

1. 这次更新是否更接近这个目标？

2. 是否增强了以下任一能力？
   - 上传资料
   - 自动分类
   - metadata 补全
   - 搜索命中
   - 知识审核
   - 知识复用
   - Agent 调用

3. 有没有偏离成“只是在做一个展示页面”？

## 四、检查用户是否能快速使用

1. 新用户打开后，是否知道第一步该做什么？

2. 用户能否在 3 步内完成核心流程？

推荐核心流程：

```text
上传资料
-> 系统生成知识草稿
-> 用户检查并保存 metadata
```

3. 页面上有没有让用户困惑的词？

4. 是否需要增加引导、空状态、按钮说明或示例？

5. 如果老师现场演示，是否能在 1 分钟内跑通一个完整案例？

## 五、检查当前功能是否形成闭环

每次迭代后检查是否跑通：

```text
输入
-> 处理
-> 输出
-> 用户确认
-> 沉淀为知识
```

对应到当前产品：

```text
上传文件
-> 后端保存
-> LLM / 规则生成草稿
-> 用户补充 metadata
-> 进入可搜索知识库
```

如果某一环断了，下一步优先修这一环。

## 六、检查下一步优化方向

每次迭代结束后，从下面选 1-2 个最重要的下一步，不要同时做太散：

1. 让真实文件更容易被系统读懂。
   - 例如接入 docx / pdf 正文抽取。

2. 让分类更准确。
   - 例如优化 LLM prompt 和 metadata 标准。

3. 让用户更快完成。
   - 例如增加上传后的自动跳转、待完善任务、三步引导。

4. 让知识更安全。
   - 例如把硬删除升级为归档或回收站。

5. 让 Agent 更容易调用。
   - 例如增加 Agent 检索接口和稳定的知识状态门槛。

## 七、每次汇报前的三句话

每次和老师汇报前，先准备好这三句话：

1. 这次迭代主要服务的用户是谁？

2. 这次迭代解决了用户什么问题？

3. 下一步怎样让用户更快达到产品目标？

## 八、当前版本的自查结论

当前 v0.2 已经从静态展示升级为轻量前后端 MVP，可以上传、入库、搜索、编辑、删除和配置模型。

但下一步还需要继续优化“快速使用”：

- 让 Word / PDF 也能自动抽取正文。
- 让 LLM 自动生成更准确的 metadata。
- 增加上传后的三步引导。
- 增加待完善草稿列表。
- 把删除升级为归档或回收站。

核心判断标准：

```text
用户上传一份真实资料后，能否尽快得到一条可搜索、可复用、可被 Agent 使用的知识条目？
```
